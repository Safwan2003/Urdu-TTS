FINE-TUNING BRIEF — Urdu Piper voice, English-loanword pronunciation
Local note. Date: 2026-09-03.

================================================================
0. WHAT AND WHY
================================================================
Production Urdu voice = Piper `ur_PK-aegis_female-medium` (VITS, espeak
`ur`, 22.05 kHz). It says plain Urdu well but mangles English loanwords:
"keypad" -> "ki pat", "transaction"/"balance" muddy.

Tried and rejected (by ear, on prod):
  - Urdu respellings (کِی پَڈ / کی پَیڈ)
  - inline espeak phonemes [[kˈiːpæd]]  -> "ki pat"
  - Latin passthrough "keypad" (current _UR_SPEAK_ENGLISH)  -> still wrong
  - reword the prompts to avoid the word  (interim, shipped for keypad)

"Adding /æ/" is the WRONG frame. espeak `ur` NEVER emits /æ/:
  "keypad"      -> kˈiːpad      (long iː, SHORT a, d)
  "transaction" -> tɹansˈakʃən
  "balance"     -> bˈaləns
Phoneme id 39 (æ) is a dead slot in this frontend; forcing it is why the
[[..æ..]] attempt failed. The target is: make the model render the a-based
English phoneme SHAPES espeak already produces (kˈiːpad, tɹansˈakʃən, ...)
cleanly. Those use ids the voice already has, just coarticulated wrong for
loanword shapes.

================================================================
1. APPROACH: LOW-RANK ADAPTATION (not a full fine-tune)
================================================================
A full fine-tune rewrites every weight -> risk of plain-Urdu regression and
voice drift on a live bank line, and you can only *hope* it didn't happen.

Instead: freeze 100% of the model, inject low-rank adapters into the text
encoder (attention q/k/v/o + FFN + proj, all `nn.Conv1d(c,c,1)` = linear),
train ONLY the adapters (~1.1% of params, ~260 K), then fold them back into
the weights at export -> a normal Piper ONNX, no runtime change.

Guarantees:
  - adapters are zero-initialised -> before training the model is bit-exact
  - scale=0 at any point -> exact original voice
  - merge is verified bit-identical to the adapted forward pass
  - the base weights are never touched, so plain Urdu cannot drift

Verified locally 2026-09-03: inject 37 convs, 263 K trainable (1.1%),
zero-init no-op confirmed, merge == adapted (max diff 0.0).

3. DATASET (the only remaining gap)
================================================================
Searched HF thoroughly — NO dataset of female Urdu speech with correctly
pronounced English loanwords exists:
  - Urdu TTS sets (mahwizzzz/UAT, HamzaSidhu...) = plain/literary Urdu
  - code-switching sets (codesaviours x12...)   = TEXT only, Roman Urdu
  - Urdu ASR sets (ASLP-lab/UrduSpeech, CV, ...) = multi-speaker, noisy, 16k

So ~120-250 clips must be made:
  - RECORD a female PK-Urdu speaker reading data/sentences_ur.txt
    (~15 min; keeps a real owned voice) — best
  - ElevenLabs multilingual, voice cloned from
    src/sdr_agent/assets/female_voice_urdu.wav -> stays Aegis-like (paid)
  - Azure ur-PK-UzmaNeural (free tier; fixed voice, not Aegis)
Because the base is frozen, NO plain-Urdu padding is needed — the corpus
is purely loanword phrases.

================================================================
4. VALIDATION
================================================================
finetune/low-rank-adaptation/verify.py renders BASE vs BASE+adapter:
  - plain-Urdu lines  -> mel-L1 ~0 (proves no regression)
  - loanword lines     -> should move, listen
Also A/B the test.md S1-S4 replies, and check the exported .onnx.json
phoneme_id_map is byte-identical (adapt_speech_text + [[..]] depend on it).
--scale lets you dial the adapter 0->1 if it over-corrects.
